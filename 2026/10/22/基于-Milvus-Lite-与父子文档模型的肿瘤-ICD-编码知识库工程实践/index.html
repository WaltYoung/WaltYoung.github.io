基于 Milvus Lite 与父子文档模型的肿瘤 ICD 编码知识库工程实践

前言

笔者在智能病案编码场景中接到一个需求：给定病历片段、诊断名或“右乳2点”这类短文本，召回候选 ICD-10 肿瘤章（C00–D48）诊断码，并给出可人工复核的命中证据。

若把整条诊断说明拼成一个长向量做检索，短查询容易被长上下文稀释，尤其是钟点、别称这类短文本；若只做精确字符串匹配，又无法覆盖同义表述。遂有此文——以工程实践为落点，介绍技术选型、父子文档模型、入库版本切换和检索聚合，并说明实际工程中的取舍。

1. 业务目标与约束

维度 约定
输入 疾病名称、诊断名称、钟点等短文本
输出 Top-K diag_code + diag_name + matched_keywords 或 evidence

当前规模约为三千条父级诊断记录、1.3 万条子向量。部署环境以内网和离线为主，模型与向量库需要能打进本地包，不依赖常驻向量服务集群。

这里的相似度是加权余弦相似度，用于候选排序和证据展示，不代表校准后的医学概率。

2. 技术选型

2.1 总体选型

项目 选择 说明
向量库 Milvus Lite 使用目录型 .db，开发和交付环境一致，适合内网单机部署
Collection tumor_kw_vectors 一行对应一个关键词子向量
嵌入模型 BAAI/bge-m3 中文短词和较长上下文表现稳定，dense 向量为 1024 维
向量维度与归一化 1024，L2 normalize 与 BGE dense 使用惯例一致，配合 COSINE
距离度量 COSINE 归一化后等价于内积，便于实现和调参
索引 FLAT 当前为万级实体，暴力检索延迟可接受
max_length 8192 尽量不截断业务侧长关键词
API FastAPI + uvicorn 提供轻量 HTTP 接口和 Swagger 文档
配置 configs/milvus.yaml 集中管理模型、库路径和版本参数

2.2 向量库选型

方案 优点 （针对本项目）短板
FAISS 纯本地、性能强 Schema、标量过滤和版本切换需要自己实现
Chroma 上手快 元数据和版本治理能力偏弱
PGVector SQL 和事务能力强 会引入数据库运维成本，不利于医院内网离线交付引入 DB 运维
Milvus Lite 与 Milvus Server 使用同一套 API；本地目录库；原生支持字段和倒排索引 后续如果数据量到百万级，再迁移到 Milvus Server

笔者判断先用 Milvus Lite 跑稳数据模型与检索契约，后续如果数据量到百万级再迁移到 Milvus Server，应用层 MilvusClient的调用方式可以复用。

2.3 嵌入模型选型

BGE-M3 支持 dense、sparse 和 multi-vector（ColBERT 风格）三种表示。三者是同一模型在一次编码中产出的不同粒度表示，区别在于用多少条向量表示一段文本，以及查询与文档在什么阶段交互。

Dense（稠密向量）：把整段文本压缩成一条固定维度的向量，每个维度均为非零值。检索时查询和文档各编码为一条向量，直接计算余弦相似度或点积。其优势是语义泛化能力强，能匹配“右乳房”与“乳腺”这类字面不同但含义相近的表达；短板是精确匹配弱，疾病代码、钟点、型号等硬信号容易被长上下文稀释，命中后也难以直接指出匹配了哪段文本。

Sparse（稀疏向量）：保留词汇级表示，每个维度对应词表中的一个词，值为该词的重要性权重，绝大多数维度为零。传统 BM25 是稀疏检索的经典形式；BGE-M3 的 sparse 模式生成的是上下文感知的类 BM25 权重。其优势是精确关键词匹配强、可解释，适合代码、专有名词、钟点等必须字面对上的信号；局限是缺乏语义泛化，难以自动识别同义表述。

Multi-vector（ColBERT 风格）：为每个 token 产出一条向量，查询和文档先独立编码成向量序列，交互延迟到打分阶段，因此称为延迟交互。打分采用 MaxSim：对查询中的每个 token 向量，在文档的所有 token 向量中找最相似的一个，再将最大值求和。它比单向量 dense 保留更细的匹配粒度，又不像 Cross-Encoder 那样对每个查询-文档对做全量注意力；代价是存储和计算开销显著更高，文档不再是一条向量，而是几十到几百条 token 向量。

表示 文本表示 匹配信号 交互时机 强项 弱项
Dense 一段文本 → 1 条稠密向量 语义相似 无（向量点积） 语义泛化、跨语言 精确匹配弱
Sparse 一段文本 → 1 个稀疏权重字典 词汇/关键词重叠 无（词项共现加权） 精确匹配 无语义泛化
Multi-vector 一段文本 → 每个 token 1 条向量 token 级细粒度对齐 延迟（编码后 MaxSim） 长查询、细粒度语义对齐 存储/计算成本高

当前实现只使用 dense，Collection 中仅保存 dense 向量，sparse 和 multi-vector 不落库，原因如下：

  1. dense + FLOAT_VECTOR + COSINE + L2 normalize 的链路简单，便于离线复现。
  2. 关键词库本身已经按词汇级切分，每个关键词对应一条子向量，这在一定程度上替代了 sparse 想解决的细粒度匹配问题；sparse 对钟点类短查询的增量收益有限，但会增加管线复杂度。
  3. ColBERT 类晚期交互对算力和存储要求更高，当前目标是候选召回和人工复核，不是榜单评测。

编码时使用 max_length=8192，CPU 和 GPU 均开启 use_fp16=True。长关键词会完整进入模型，编码速度较慢，但通过 content_hash 缓存可以断点续跑。

2.4 索引选型

在本项目中主要考虑以下三点：

  1. 规模：当前子向量在万级以内，FLAT 的扫描延迟可以接受。
  2. 工程现实：在 Windows 系统上并且仓库路径包含中文时，HNSW/IVF 落盘曾出现不稳定。
  3. 可预期性：FLAT 没有近似误差，评测和排障更直接。

规模上升后，优先选择 IVF_FLAT 或 HNSW，并使用 Linux 绝对路径部署。

3. 父子文档模型

3.1 概念定义

概念 含义
父文档 一条 ICD 诊断，包含诊断代码、名称、系统或器官等字段以及关键词
子文档 每个去重后的关键词编码为一条向量；同一 diag_code 对应多行实体
检索单位 子向量
返回单位 父级诊断码

3.2 不直接用全文向量的原因

如果把诊断码、名称、部位、钟点和临床特征拼成一段文本再编码，会存在三个问题：

  • 短查询与长拼接文本的相似度被稀释
  • 钟点、别称等窄信号容易被噪声淹没
  • 命中后难以说明到底匹配了哪段证据

父子模型把检索粒度下沉到关键词，把返回粒度保留在诊断码，既保证短查询召回，也方便展示证据。

3.3 使用多行实体的原因

Milvus Collection 的 Schema 字段数固定，但一条诊断的关键词数量不固定。

  • 如果使用多向量列：容易造成字段数膨胀或被迫截断到固定数量；
  • 如果使用多行实体，每行保存一个 (diag_code, kw_text, vector)，可以自然适配变长关键词。

3.4 子行类型与权重

解析后对关键词打标，但不丢弃：

kw_type 规则 检索权重
name 等于诊断名称 1.0
clock 钟点正则，如“右乳2点”“3-5点” 0.95
raw_kw 其他关键词，包括长上下文 0.9

聚合时计算 fused = cosine_score × weight，cosine_score是 Milvus 检索阶段返回的、查询向量与某条子向量之间的余弦相似度，同一 diag_code 取 Max(fused)。

使用 Max 而不是 Sum 或 Mean 的原因：

  • Sum 会让关键词数量多的诊断码占优；
  • Mean 会被大量弱匹配拉低，强证据可能被淹没；
  • Max 以最强单条证据代表该诊断码，与“给出一条命中证据”的产品需求一致。

3.5 与常规 RAG 分块方案的区别

本方案在结构上类似 RAG 中常见的父子检索思路，但切分依据和返回目标不同。

常规 RAG 本方案
将长文档按长度或标题切分成若干片段 将诊断说明拆成专家整理的关键词
对文本片段做向量检索 对关键词子向量做检索
命中后回填片段原文 回填 diag_code 和命中的 kw_text

两者的主要区在于：常规 RAG 的文本片段多由通用规则切分，目的是给大模型提供上下文；本方案的子文档是编码知识中的业务关键词，包括诊断名、钟点、别称和长上下文，目的是提高短查询的召回效果，父文档保留 ICD 诊断码这一业务主键，便于聚合结果。

4. 端到端流水线

阶段 脚本 输入 输出
解析 scripts/text2json.py data/raw/*.txt data/parsed/parsed.jsonl
编码 scripts/json4embed.py parsed.jsonl data/embeddings/embeddings.jsonl
入库 scripts/embedding2db.py embeddings.jsonl data/milvus/tumor_ch2.db
检索 services/main.py HTTP query Top-K 诊断及证据

编码阶段使用 content_hash = sha256(diag_code + '\0' + kw_text)，并拼接上 model_name|dim 作为缓存键，以支持断点续跑。

.db、embeddings、parsed 等本地大产物不进入 Git。离线包中模型目录和向量库各自独立，可以分开上传。

6. 检索服务：子向量召回与按码聚合

检索流程如下：

  1. 查询时使用与入库相同的 BGE-M3 进行编码。
  2. 调用 Milvus search(limit=candidate_k)，默认 candidate_k=80。
  3. 对每个命中计算 fused = cosine_score × weight[kw_type]。
  4. 按 diag_code 保留 Max(fused)，并收集该码下的命中词，按加权分排序取前 5 个。
  5. 全局排序后截断 top_k，默认 5。

请求示例：

响应中的 score 是聚合分，evidence 取该诊断码下加权分最高的命中词文本。

candidate_k 和 top_k 分开设置，是因为聚合前需要多召回一些子行。否则同一诊断码的多个关键词可能挤占候选名额，其他诊断码无法进入候选池。经验上从 candidate_k ≈ 10～20 × top_k 起步，再根据测试结果调整。

模型采用懒加载：/health 先检查库是否可用，第一次 /search 时再加载 BGE 模型，缩短冷启动和打包探活时间。

7. 版本化与版本切换

入库时不直接覆盖正在服务的库文件，而是先写入版本库，确认写入完成后再切换到服务路径。具体流程如下：

  1. 写入 data/milvus/{kb_version}.db。
  2. 执行 drop/create、insert、flush、load。
  3. 关闭 Milvus client。
  4. 将版本库替换为 data/milvus/tumor_ch2.db。

第 4 步在 Windows 下可能遇到文件锁，因此采用先复制、再改名的方式：

  1. 将版本库复制为 tumor_ch2.db.tmp_promote。
  2. 将当前 tumor_ch2.db 改名为 tumor_ch2.db.bak。
  3. 将 tumor_ch2.db.tmp_promote 改名为 tumor_ch2.db。

服务启动时只读取配置中的当前 URI，不感知版本目录名。运维流程为：重建版本库、版本切换、重启服务。

当前增量策略如下：

层级 策略
Embedding JSONL 级 hash 缓存续跑
Milvus 全量重建，不做 upsert 差分

选择全量重建的原因：

  1. 万级实体重建成本低，一致性好；半增量同步容易留下不应存在的子向量
  2. 向量化的主要成本在 embedding，不在写库。

8. 常见问题与设计取舍

Q1：父子文档和普通文本分块有什么区别？
普通文本分块通常按长度或标题切分，目的是给大模型提供上下文。本项目的子文档是编码知识中的业务关键词，包括钟点、别称和长上下文；父文档是 ICD 诊断业务主键。切分依据来自医疗领域语料结构，不是通用文本切窗。

Q2：为什么加权聚合使用 Max？会不会漏掉多个关键词同时命中的情况？
Sum 会让关键词数量多的诊断码占优；Mean 会被大量弱匹配拉低，强证据可能被淹没。取 Max 确实可能漏掉多个关键词同时命中的情况。如果业务确认多证据同时命中应当加分，可以改为 Max + λ·log(1+#hits)，或对前 m 条证据做有界求和，但需要先建立测试集验证效果。

Q3：为什么不在线使用 Cross-Encoder 重排？
当前定位是高召回候选加AI筛选。Cross-Encoder 能提升排序效果，但会增加延迟和模型运维成本。后续可以在聚合后对 Top-N 诊断做二阶段重排序。

Q4：FLAT 如何保证性能？
FLAT 复杂度为 O(N·d)。N 约为 1e4、d=1024 时，单次扫描通常在毫秒到十几毫秒级。实际瓶颈在 BGE 编码，而不是检索。优化顺序应是批处理、模型量化或 ONNX，再考虑更换索引。

Q5：如何保证入库向量和查询向量一致？
编码和查询服务共用 scripts/embed_model.py，配置文件固定 model_name、dim、normalize 和 max_length。更换模型必须修改 kb_version 并全量重编码，不混用旧库。

Q6：content_hash 能否用于增量 upsert？
可以用于差分设计，但当前仍选择全量重建。如果要改为增量更新，需要以 content_hash 作为业务键执行 upsert，并显式处理父记录删除关键词时的删除集，否则库中会残留不应存在的子向量。

Q7：建了倒排索引为什么不用 filter？
当前预留了按诊断码或类型过滤的能力，但过早使用 filter 可能误杀，因此先走纯向量召回，等有明确业务规则后再添加。

Q8：如何评测这套知识库？
构造标准数据，格式为 (query, diag_codes[])，统计 Recall@K、MRR，以及命中的证据词是否落在可接受集合内。钟点类和别称类查询应单独分类统计，避免被普通诊断名查询的平均结果掩盖。

9. 已知局限与后续改进

现状 风险与改进方向
无正式评测集 调 top_k 和权重主要靠经验
无 Cross-Encoder 精排上限受限；可作为二阶段
钟点主要靠关键词入库和轻微加权 可叠加规则预检或结构化钟点解析
全量重建库 语料频繁小改时成本偏高；可做 hash 差分 upsert
BGE 仅使用 dense 可评估 sparse 混合召回，尤其是别称场景
FLAT 规模上升后迁移 IVF/HNSW，并使用 Linux 路径

写在文后

本文实现的知识库是一套完整的父子文档模型的实现：父文档定义业务对象，子文档定义检索粒度，加权 Max 定义排序语义，版本库与 promote 定义发布方式。

工程上需要重点关注的是

  1. 为什么选择检索粒度与返回粒度不一致？
  2. 为什么使用多行实体而不是多向量列？
  3. 为什么聚合使用 Max 而不是 Sum？
  4. 为什么当前规模下 FLAT 是合理选择？
  5. 如何保证 embedding 入库与服务查询一致，避免换库时出现半更新？
